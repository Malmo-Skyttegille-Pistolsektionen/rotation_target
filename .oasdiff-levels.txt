# Severity overrides for oasdiff, one "<check-id> <level>" per line.
#
# response-property-enum-value-added
#   Default WARN, which with `fail-on: WARN` fails the build for every added
#   value. Downgraded to INFO because `Problem.type` is an open vocabulary and
#   openapi.yaml says so where the enum is declared:
#
#     "The enum is the whole vocabulary. It is open in practice: a client must
#      fall back to `status` and `detail` for a value it does not recognise,
#      because new types are additive and a client may be older than the
#      firmware it is talking to."
#
#   So adding a problem type is additive by the contract's own rule, and every
#   pull request that adds one would otherwise fail. #144 was the first to hit
#   it, with nothing breaking about it.
#
#   oasdiff suggests `x-extensible-enum` instead of this override, and that is
#   the better answer in general - but not here. `openapi-typescript` builds
#   the webapp's `ProblemType` union from `enum`, and the mock server's
#   `satisfies Record<ProblemType, ...>` uses that union to make a problem type
#   present in the contract but missing from the mock a compile error. It has
#   already caught a real omission. `x-extensible-enum` is not standard
#   OpenAPI, the generator would emit `string`, and that check would go.
#
#   Deliberately narrow: request-side enum additions keep their default level.
#   A value a client may now *send* is a different question from one it may now
#   *receive*.
response-property-enum-value-added    info
